# Core Spec 五门质量检查表

本文件是 core-spec skill 的完整验收判据。五门全部满足，spec 才能从 `draft` 切换为 `authoritative`；审计时按本表逐项打分并输出证据。

---

## G1 精确与可追溯

**目标：** 规范性条款没有第二种读法，每条需求都能定位到唯一 ID 和验收标准。

- [ ] 全文无模糊词：可能、大概、尽量、友好、快速、及时、合理、适当、支持等词不得出现在规范性条款；确需表达概率/范围时给出数值（P95、±10%、≤5s）。
- [ ] 每条功能需求有唯一 ID（`REQ-<n>`），且 ID 不重复、不复用已删 ID。
- [ ] 每条需求包含：角色 + 动作 + 价值（用户故事），以及 `Given/When/Then` 验收标准。
- [ ] 每条需求标注优先级（P0/P1/P2）。
- [ ] 时间、容量、次数、状态数全部是具体数值；禁止“若干、多个、一批”。
- [ ] API/数据结构示例完整：请求、响应、错误路径至少各一例。
- [ ] 正文无实施波次标识：`W0–W8`、`S0–S5`、“第 N 波次”等只允许出现在 `plans/` 或 roadmap，不得出现在权威规格正文。

## G2 异常与 NFR 完整

**目标：** 不只写 Happy Path；上线后最常见的故障模式在 spec 里有规定。

- [ ] 每个状态都有：进入条件、退出条件、可观察结果、失败分支。
- [ ] 状态图中每个转换都写了触发条件、guard、action、失败时去向。
- [ ] 错误模型覆盖：未入队/入队后断线/超时/取消/重复回包/过期代际/资源耗尽，并区分“事实”与“建议”。
- [ ] NFR 单独成节且量化：
  - 性能：延迟（含 P95）、吞吐、并发；
  - 可用性：恢复窗口、重试次数、退避上限、降级行为；
  - 安全：认证、授权、敏感数据、日志脱敏、限流；
  - 合规/保留：数据保留周期、清理策略；
  - 容量/背压：队列上限、溢出行为、无界扩容禁止项。
- [ ] 明确“不做自动重放/自动恢复”的边界，把重试决策留给知道幂等语义的一层。

## G3 内部一致

**目标：** 图、表、正文、验收标准、目标/非目标是同一套语义；一个术语只有一个定义。

- [ ] 术语表覆盖所有规范性名词；同一概念全文只用同一个词（含代码标识符）。
- [ ] 同一数值的两口钟必须分术语。禁止用「都是 Ns」把不同身份写成一个（例如脱节等待与 Call 等回包、L0 PongWait）。
- [ ] 同一类型/方法/错误在全文只有一处权威定义，其余地方只引用，不复述签名。
- [ ] 状态图、状态表、正文规则、验收标准相互一致；任何一处修改必须同步其余各处。
- [ ] 被取代条款已原地合并或删除；权威规格正文不得出现“（已被 Dxx 取代）”“补丁标记”字样。
- [ ] 正文无实施步骤与实现级设计：迁移步骤、锁算法、波次推进等要么移入 plans/，要么压缩为可验证的一句话契约。
- [ ] 目标/非目标与最终验收一致；若验收推翻早期目标，早期目标必须改写，不能并存。

自检方法：把 spec 中每个状态、错误、方法名列成清单，逐一对照代码与验收；发现两个来源说法不同即 P0。

## G4 验证实测全绿

**目标：** spec 的每一条关键契约都有机器证据，且这些证据在提交时真实跑过。

- [ ] `tools/audit_spec.py` 存在且 PASS（结构审计）。
- [ ] `tools/test_audit_spec.py` 存在且 PASS（审计器负例自测：每类违规都要有 fixture 能让审计器失败）。
- [ ] `tools/barriers.py` 存在；spec 为 authoritative 时必须实际运行且全绿，禁止只写命令不运行。
- [ ] manifest 中声明的每个测试锚点都能在代码中 grep 到真实测试函数名；缺失即失败。
- [ ] manifest 中声明的代码契约 pattern 与代码一致；旧签名/旧 sentinel 已列入 obsolete 且零命中。
- [ ] 新增/修改 spec 后，spec 与代码同批提交，审计命令输出写入提交说明或验证记录。
- [ ] 存量 spec 迁移时保留已通过验证的既有工具，只改 canonical 文件名与路径，不得替换成模板实现；旧全局脚本在新位置全绿后才删除。

## G5 治理与元信息

**目标：** 任何一条规范都能回答“为什么这么定、哪次变更定的、现在是否还成立”。

- [ ] 每条规范性契约都能归因到决策日志中的决策 ID（D01、D02…）。
- [ ] 决策 ID 范围全文档一致；不得出现“覆盖 D01–D24”而实际已有 D25 的过期引用。
- [ ] 头部元信息完整：状态（draft/authoritative）、版本、受众、范围、治理规则、变更历史指针。
- [ ] 变更日志/历史指针存在：git 可追溯之外，history/ 或决策日志能定位每次行为变更。
- [ ] Out of Scope 明确列出本次不做的事，防止范围蔓延。
- [ ] 提交遵循仓库 AGENTS.md 约定（提交信息、签名方式、spec 与代码同批）。

## 常见借口与回应

| 借口 | 回应 |
|---|---|
| “这段行为代码里已经很清楚，spec 不用写” | spec 是唯一权威，代码只是当前实现；不写就无法发现漂移。 |
| “审计器 PASS 了，所以没问题” | 词法/结构检查不覆盖语义矛盾；G3 必须人工/契约对照。 |
| “先把旧条款留着，标注已取代，以后再清理” | 一份文档两套语义；保留旧条款的收益永远低于误读成本。 |
| “这个测试名计划里会补，先写进 spec” | 允许 draft 状态声明 planned，但 authoritative 前必须真实存在且 barriers 全绿。 |
| “验证命令跑过了，只是没记录” | 没有可复现输出等于没有验证；把命令与结果写进提交说明。 |
| “spec 已经写了就必须照做，不能停” | spec-first 不是条款不许质疑。身份分层错误、What/How 混写、决策假设被推翻时，立即告知用户商量是否改 spec；确认前不得一条路走到黑。 |

## 审计输出格式

审计报告至少包含：

1. 验证命令与真实输出（audit_spec / test_audit_spec / barriers）。
2. P0/P1/P2 分级问题清单，每条带 spec 行号与代码/测试证据。
3. 整改顺序：先语义、再契约、再可验证性、再元信息。
4. 明确结论：`draft` / `authoritative` / `需回退重审`。
