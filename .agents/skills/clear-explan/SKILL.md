# clearExplan

先判断场景，再选图。禁止把「改哪些文件」的计划树套到「这段代码现在怎么跑」上。

**进度不在本技能：** 用户问「跑到哪了」→ 读 `progress.md` 和 plan checkbox。

## 场景（第一步，必须选一个）

| 场景 | 用户在问什么 | 典型说法 |
|---|---|---|
| A 计划图景 | 准备改什么、改完长什么样、计划怎么来的 | 「设计是什么」「模块规划」「按审查准备怎么改」「来龙去脉」 |
| B 技术细节 | 仓库里一个符号现在怎么被调用、何时发生、对端收到什么 | 「X 是谁发的」「什么时候发」「是发给前端/客户端吗」「通过什么发的」 |

混合提问：先 B（把机制讲清），用户要改动图景再 A。不要两套图搅在一段里。

**不要用本技能：** 未主动要求结构/机制时；往 plan 文件里自动插图；单一文件机械改动。

~~旧规则「已经在讨论实现细节就不要给概览」作废。~~ 实现细节走场景 B，必须给调用树。

## 反抽象（两场景共用）

用户懂技术、不懂本仓库。禁止自造词、比喻、门牌/销户之类。术语第一次出现用括号补一句「这是干什么」。函数名可保留，旁边必须有大白话。纯 ASCII 树（`├──` `│` `└──`），不用 Mermaid/emoji。

---

## 场景 A — 计划图景

决策者 30 秒要看到：改哪些文件、关键路径旧/新、多端怎么对应、放弃了什么。不要写测试命令（那是 plan 正文）。

默认出图 1 + 图 2；多端再出图 3；问「怎么来的」再出图 4。图前一句说明这张图回答什么。

**图 1 文件规划：** 每个文件一行职责。`← 新建（…）` / `← 修改（…）`。变更点标 `旧:` `新:`。

**图 2 调用链：** 从入口到结果，只画关键路径，标旧/新为什么旧的不行。

**图 3 对称表：** 仅多端/多模块。对齐项逐行，差异单独一段。

**图 4 来龙去脉：** 按日期写发生了什么、决定了什么。不写规格决策 ID。列出放弃的方案和原因。

禁止：把计划树里的「新建包」编造出来（仓库里没有的目录不要画进去）。

## 场景 B — 技术细节

先读代码再说话。禁止凭记忆编「发给前端/发给客户端」。

回答顺序固定：

1. **三句（必须先写，必须有代码依据）**
   - 谁调用（文件 + 函数名）
   - 是不是网络包（进程内 `Apply`/函数调用，还是 WebSocket/HTTP）
   - 对端实际收到什么（被管客户端 / 管理端浏览器 / 谁都收不到这个名字）
2. **一张调用树**  
   从真实入口画到真实出口，节点必须是 grep 到的符号。旁注大白话。
3. **只有用户追问时**再补第二条路径、订阅者名单、UUID 比对规则。

场景 B **禁止：**

- 出图 1「文件规划（新建/修改）」——那是计划，不是现状
- 比喻
- 先讲四个假设场景再讲定义
- 未 grep/read 就回答「发给谁」

管理端若最终能「看见」结果，必须写清中间层：领域事件 → 哪个订阅者 → 哪个投影 → 哪条 channel topic。不要把内部命令说成前端协议。

## Common Mistakes

| 错误 | 后果 | 正确 |
|---|---|---|
| 用场景 A 的改文件树回答「X 是什么」 | 用户以为在听现状，实际在听还没做的计划 | 先三句 + 现状调用树 |
| 未读代码就猜发给前端/客户端 | 把进程内命令说成协议 | grep 调用点后再说 |
| 内部命令和 OFFLINE 混谈 | 以为会杀客户端进程 | 分开：谁发、是不是帧 |
| 比喻（门牌、销户） | 越听越乱 | 用符号名和层名 |
| 实现细节不画树 | 只剩散文，关系理不清 | 场景 B 必须有调用树 |
| 计划树里出现仓库没有的包 | 决策者按幻觉目录想问题 | 只画真实路径 |
| 把「实现细节不给概览」当成可以不画树 | 技术问题用散文敷衍 | 细节走场景 B |
