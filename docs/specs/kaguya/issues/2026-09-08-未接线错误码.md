# 错误码 user.invalidShell 与 view.invalidField 已定义未接线 — Issue

**状态:** open
**发现日期:** 2026-09-08
**最后更新:** 2026-09-08
**来源:** 代码审计（core-spec 落地时根植腿核对）
**关联章节:** §5（错误模型）、REQ-009、REQ-004
**关联决策 ID:** 未归因

## 1. 现象

`lib/errors.nix` 的 zh-CN 与 en-US 两个 bundle 均定义了 `user.invalidShell` 与 `view.invalidField` 的渲染器，但 `lib/capGraph.nix` 中不存在以这两个错误码为 `code` 的 `throwError` 调用。

## 2. 证据链

| 证据 | 位置 |
|---|---|
| `user.invalidShell` 渲染器定义（zh-CN、en-US） | lib/errors.nix:9、lib/errors.nix:36 |
| `view.invalidField` 渲染器定义（zh-CN、en-US） | lib/errors.nix:24、lib/errors.nix:51 |
| 全 lib/ 目录无这两个错误码的抛出点（grep 仅命中 errors.nix） | 2026-09-08 核查 |
| shell 枚举校验实际走 `ensureEnum` → `node.invalidEnum` | lib/capGraph.nix `normalizeUser`（shell 字段）与 `ensureEnum` |
| view 字段类型校验实际走 `node.invalidType` | lib/capGraph.nix `loadViewFacet` |

## 3. 根因

判定：历史遗留的预留错误码。用户 shell 与视图字段校验在实现上复用了通用校验器（`ensureEnum` / `ensureListOfStrings`），未使用专用错误码。已确认，非猜测。

## 4. 影响

- spec §5 已将两码标注为"保留"，行为不受影响；实际触发路径为 `node.invalidEnum` / `node.invalidType`，与 §5、§7（E03、E13）的现行描述一致。
- 若后续有人按错误码表面实现消费逻辑（如按 `user.invalidShell` 过滤日志），将永远匹配不到。

## 5. 建议

- 代码层：二选一——将 `normalizeUser` 的 shell 校验改为抛 `user.invalidShell`（需扩展 `ensureEnum` 支持自定义错误码），或删除两个未接线渲染器。
- spec 层：任一选择都需要 §9 新增决策 ID 归因后修改 §5 表；本 issue 在闭环时填写该决策 ID。

## 6. 闭环记录

- open：等待上述二选一决策；无阻塞中的框架变更依赖本项。
