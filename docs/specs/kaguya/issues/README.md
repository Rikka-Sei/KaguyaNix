# issues/ 使用规则

本目录登记 core spec 生命周期中发现的、尚未通过决策日志闭环的问题与风险。目录内文件是**调查记录**，不是规范性正文；spec 行为仍以 `spec.md` 和 §9 决策日志为唯一权威。

## 目录规则

- 一个问题/风险一个文件，文件名 `YYYY-MM-DD-<中文短slug>.md`；日期为首次登记日期，slug 概括问题主题。
- 状态原地流转，不迁移到 `history/`：

| 状态 | 含义 | 必填 |
|---|---|---|
| open | 已记录，未闭环 | 除关联决策 ID 外全部字段 |
| resolved | 已通过 spec/代码/部署变更闭环 | 关联决策 ID + 验证结果 |
| wontfix | 确认不接受处理 | 关联决策 ID + 拒绝理由 |

- `resolved`/`wontfix` 必须填写 §9 决策日志中的决策 ID。
- issue 文件可被 spec 正文或审计报告引用，但引用只作定位，不作为行为依据。
- 与问题无关的变更不得顺带修改 issue 状态。

## 文件骨架

```markdown
# <问题标题> — Issue

**状态:** open / resolved / wontfix
**发现日期:** YYYY-MM-DD
**最后更新:** YYYY-MM-DD
**来源:** 线上日志 / 代码审计 / 测试失败 / 用户反馈
**关联章节:** §x.y（或 REQ-xxx / 阶段名）
**关联决策 ID:** 未归因（open） / Dxx

## 1. 现象

[可复现日志/报错/测试输出，保留关键标识]

## 2. 证据链

| 证据 | 位置 |
|---|---|
| [证据描述] | [file:line 或外部文档链接] |

## 3. 根因

[结论与判断依据；未确认时明确标注“待确认”，不得与确认结论混写]

## 4. 影响

[范围、阶段、是否符合 spec 现有规定]

## 5. 建议

[按部署/运行、代码、spec 分层；写明是否需要新增决策 ID]

## 6. 闭环记录

- open：记录等待依据。
- resolved：变更摘要 + 决策 ID + 验证结果。
- wontfix：拒绝理由 + 决策 ID。
```
